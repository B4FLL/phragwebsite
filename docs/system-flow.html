3Step-by-step flows

Open a flow to see each step, who does it, and which file or table is involved.

Sign in and get a role login.js · auth.js · members.sql

Members sign in with an email link, no password. The site then asks the database whether that email is an editor or an expert.

  1. BrowserPerson types their email on the Members page and presses the button. sb.auth.signInWithOtp asks for a link that returns to the same page.login.js
  2. SupabaseAuth emails a one-time link. Opening it signs the person in (a session in the browser).
  3. BrowsergetMember() reads the session, then asks is_editor and is_expert at the same time.auth.js
  4. DatabaseThe functions look up the person's lowercased email (from their verified sign-in) in member_emails, or their user id in the older editors / experts tables.supabase/members.sql
  5. BrowserPage shows or hides editor and expert features. If a check fails it retries once, then uses the last good answer for this tab. If there is none, it says it couldn't check instead of silently hiding features.

Anyone who signs in is a normal signed-in member. Roles only come from an admin adding the email to member_emails in the Supabase dashboard. The website itself cannot read or change that list.

View the map map.js

The map combines four sources into colored dots, and filters them in the browser without asking again.

  1. BrowserReads data/inat-utah.json and data/gbif-utah.json (static files). Records are colored by subspecies; ones older than 5 years are drawn faded.
  2. DatabaseReads public_reports: community sightings with coordinates rounded to about 1 km, rejected ones removed.supabase/schema.sql
  3. DatabaseReads public_posts for purple neighbor-photo pins; photo files come from the public community-photos bucket.
  4. OutsideDraws street or satellite tiles; the search box asks Nominatim for Utah addresses.
  5. BrowserIf one source fails, the others still show and the stats line says which failed.
Report a sighting, then expert review map.js · schema.sql

Anyone can report a sighting. It appears on the map as "unverified" until an expert checks it.

  1. BrowserVisitor places a pin inside Utah, fills date, ID guess, patch size, notes and an optional name. A hidden spam-trap field must be empty.
  2. DatabaseInsert into reports. The rule only allows status = 'unverified', with no expert note. Checks also enforce Utah bounds and no future dates.
  3. ExpertOn the map page the expert review queue reads reports directly (exact coordinates) for rows still unverified.
  4. ExpertPresses Verify or Reject with an optional note. The row gets the new status, expert_note and verified_by.
  5. Databasepublic_reports now shows the report as verified, or hides it if rejected.

The public never reads the reports table. It reads the rounded view, so exact spots on private land stay hidden.

Post a neighborhood photo community.js · community.sql

Signed-in people share a photo with a location. The saved copy is re-drawn so hidden camera data never reaches the site.

  1. BrowserPerson chooses a photo (JPG, PNG or WebP, up to 25 MB before shrinking). exifr reads its GPS position and date, if it has them.
  2. BrowserThe location comes from the photo, a click on the small map, the device location, or an address search (Nominatim). It must be inside Utah.
  3. BrowserThe photo is shrunk to at most 1600 px wide and re-saved as JPEG at 82% quality. This drops hidden data such as GPS.
  4. StorageUploaded to community-photos/<user id>/<time>-<random>.jpg. People can only upload into their own folder.
  5. DatabaseInserts a row in posts (name, location, precise flag, date, ID guess, caption, image path). A trigger refuses more than 10 posts per hour.
  6. BrowserIf the insert fails, the just-uploaded photo is deleted so no orphan is left. Otherwise the feed reloads.

Public location is rounded to about 1 km unless the poster ticked "show my exact location". Only the poster, experts and editors can read the exact spot.

Read, comment, hide and report community.js · community.sql

Anyone can read the feed. Signed-in people can comment and report. Moderators can hide.

  1. DatabaseThe feed reads public_posts (newest 100, visible only). The view rounds locations, hides user ids, adds comment_count, is_mine, and author_is_expert, which is worked out inside the view from the expert lists.
  2. Browser"Near me" sorts by distance from the device location in the browser; the location is not sent anywhere.
  3. DatabaseOpening comments reads public_comments. A signed-in person can add one (limit 30 per hour) or delete their own.
  4. Database"Report" inserts into flags (once per person per item, 20 per hour). The Report button only appears after the flags table exists.
  5. Expert / editorSees reasons under flagged items. "Hide" updates only status and hidden_by; the item leaves the public feed but stays in the database.
  6. StorageWhen an author deletes a post, the row is deleted and then its photo file is removed.
Edit the website text and photos cms.js · cms.sql

The HTML holds the starting text. Whatever editors save in the database overrides it for everyone.

  1. DatabaseOn every page with editable spots, cms.js reads all rows of site_content (open to everyone) and fills each data-edit text and data-edit-img photo slot by its key. Empty optional cards and list items stay hidden from visitors.
  2. BrowserIf the person is an editor, an "Edit page" bar appears. Text becomes plain-text editable; photos can be added or removed.
  3. BrowserA new photo is shrunk to JPEG (this removes GPS data) and the editor is asked for a short description that is read aloud to blind visitors.
  4. StorageOn Save, new photos upload to site-images (editors only).
  5. DatabaseChanged items are written to site_content with an upsert on key. A trigger also copies every version into site_content_history, so a bad edit can be recovered.
Automatic weekly jobs .github/workflows/

Two scheduled jobs keep the map data fresh and the free database from pausing.

  1. Monday 09:00 UTCRefresh job starts on a Windows runner and downloads Utah Phragmites records from iNaturalist and GBIF (location, date, taxon and link only: no photos or usernames).
  2. CheckIf iNaturalist has fewer than 800 records or GBIF fewer than 80, the job stops and publishes nothing.
  3. CommitIf the files changed, the job commits data/ to the repository, and GitHub Pages serves the new files. Those commits also keep the schedule from being switched off after 60 quiet days.
  4. Mon and ThuThe keep-awake job reads one row from public_reports. If the project was paused it fails, and GitHub emails the repository admins.

5Demo mode

If supabaseUrl or supabaseKey in config.js is empty, auth.js sets demo = true and no Supabase client is made. Every page then uses the same store functions but saves to the visitor's own browser (localStorage), so nothing is shared.

Keys used: phragReports, phragPosts, phragComments, phragFlags, phragDemoMember (the "demo member" button), plus phragName (remembered display name) and the page-text store used by cms.js. Photos are kept as data URLs there. The live site is connected to Supabase, so it is not in demo mode.
