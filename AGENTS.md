# Repository Guidelines

## Project Structure & Module Organization
Static site (no bundler, no package.json) hosted on GitHub Pages, backed by Supabase. Pages are plain HTML + vanilla JS loaded via `<script>` tags; the Supabase client comes from a CDN global (`window.supabase`).

- `config.js` sets `window.PHRAG_CONFIG` (Supabase URL + publishable key). Both are public by design; never put a `secret`/`service_role` key there. Leaving them empty enables **demo mode**, where `auth.js` and the pages fall back to `localStorage`. Keep demo-mode paths working when changing data code.
- `auth.js` creates the single Supabase client and exposes member lookup (`getMember`: roles via `is_editor`/`is_expert` RPCs, with retry and cached fallback). Pages depend on it; load it first.
- `cms.js` is in-page editing: any element with `data-edit="key"` or `data-edit-img="key"` is editable and saved to `site_content`. HTML text is only the default; saved values override it.
- `map.js`/`map.css` (Leaflet map, reports, expert verification), `community.js`/`community.css` (photo feed, comments, flags), `geocode.js` (address search).
- Security lives in `supabase/*.sql` (row-level security, public views like `public_reports`/`public_posts`, storage). Run in order: `schema`, `cms`, `members`, `community`, `herds`; scripts are re-runnable. Schema changes need matching client updates and a README note.
- `data/*.json` are generated by `scripts/fetch-inat.ps1` and `scripts/fetch-gbif.ps1`; don't hand-edit. The weekly workflow commits them.

## Build, Test, and Development Commands
- Serve locally (the map uses `fetch`, so don't open files directly): `python3 -m http.server 8000`, or VS Code Live Server.
- Refresh data: `powershell -ExecutionPolicy Bypass -File scripts/fetch-inat.ps1` (and `fetch-gbif.ps1`).
- CI: `.github/workflows/refresh-data.yml` (weekly, Windows, fails if record counts are too low) and `keep-database-awake.yml` (parses `config.js` with grep, so keep the `supabaseUrl: "..."` / `supabaseKey: "..."` format).

## Coding Style & Naming Conventions
No linter, formatter, or type checker is configured. Match existing style: plain ES (IIFEs, `async/await`), two-space indent, double quotes, explanatory header comments. Store only location, date, taxon and link for observation data (no photos or usernames). Plain-text editing only in CMS fields. Photos are re-encoded client-side to strip EXIF.

## Testing Guidelines
There is no automated test suite. Verify changes manually in a local server, in both demo mode (empty `config.js` values) and connected mode. For layout bugs, `tests/mobile-menu.check.js` is a Playwright phone-width check; see `docs/testing.md` for results and how to run it.

## Commit & Pull Request Guidelines
History uses short, imperative, capitalized subjects without prefixes (e.g. "Fix community views: compute expert tag inline so visitors can read them"). Work is committed directly to `main`; there is no PR template. Update `README.md` when behavior, setup steps or SQL files change.
